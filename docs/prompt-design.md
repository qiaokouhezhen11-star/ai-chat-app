# Prompt Design

## 概要

このアプリでは、クライアントから送られた会話履歴をそのままOpenAIに渡すのではなく、サーバー側で整形したうえでプロンプトを構成しています。  
目的は、回答品質の安定化と、不正またはノイズの多い入力の影響を減らすことです。

## 基本構成

OpenAIへ渡すメッセージは、次の順番で組み立てています。

1. 固定の `system` メッセージ
2. 添付ファイルがある場合は、ファイル内容を含む `system` メッセージ
3. 整形済みの会話履歴

## 固定system promptの役割

固定の `system` メッセージでは、主に次の方針を指定しています。

- 日本語で分かりやすく回答する
- 初心者にも理解しやすい説明にする
- 手順を1つずつ提示する
- コマンドやコードはそのまま使える形で出す
- アップロードファイルがある場合は、その内容を優先して扱う
- リアルタイム外部情報が取れない場合は、確認したふりをしない

この方針により、単なる雑談AIではなく、学習や作業支援に向いた出力を狙っています。

## ファイル参照の設計

添付ファイルがある場合は、ファイル本文を追加の `system` メッセージとして注入しています。  
これにより、会話履歴とは別に「参照すべき前提情報」を明示できます。

採用している理由は次の通りです。

- 実装がシンプル
- 添付文脈を明示的に分離できる
- 通常のチャット履歴と責務を分けやすい

## 入力整形

サーバー側では、受信した `messages` をそのまま使わずに、次の整形を行っています。

- 配列であることを確認
- `role` が `user` / `assistant` / `system` のいずれかか確認
- `content` が文字列か確認
- 前後空白を除去
- 空文字メッセージを除外
- 履歴を直近20件に制限

これにより、フロント状態の揺れや意図しないデータ混入の影響を減らしています。

## モデル選択

現在はサーバー側で許可したモデルのみ受け付ける構成です。  
クライアントが任意のモデル名を送っても、そのまま通さないことで安定性を担保しています。

## 続きを生成する設計

「続きを生成」は、直前の出力を踏まえて自然につながるよう追加プロンプトを作る方式です。  
完全な状態復元ではなく、ユーザーが使いやすい操作性を優先しています。

## この設計のメリット

- 出力方針を安定させやすい
- ファイル付き会話でも回答の方向性を保ちやすい
- サーバー側で安全に入力を制御できる
- クライアント実装を複雑にしすぎずに済む
